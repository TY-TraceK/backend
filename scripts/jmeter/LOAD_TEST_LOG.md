# TraceK 부하테스트 기록

`tracek-load-test.jmx` 실행 결과를 회차별로 기록. 원본 리포트/raw 로그는
`scripts/jmeter/results/<회차>/`에 로컬 보관 (용량 문제로 git 추적 제외, `.gitignore` 참고).

## 1차 (Baseline) — 2026-08-14

- **실행 위치:** 로컬 PC → EC2 퍼블릭 IP(13.210.218.196:8080)
- **구성:** 1_전체_API_흐름(50 threads, 5 loop) + 2_핫스팟_동시_좋아요(같은 location_id에 서로 다른 유저 100명 동시 PUT)
- **원본:** `scripts/jmeter/results/baseline/result_baseline.jtl`, `report_baseline/index.html`

### 목표 SLA (사후 정의 — 테스트 후 기준을 세우고 실측과 대조)

| 항목 | 목표 | 실측 | 판정 |
|---|---|---|---|
| 에러율 (HTTP) | 0% | 0% | PASS |
| 평균 응답시간 | < 500ms | 313ms | PASS |
| p95 응답시간 (서버 측) | < 1s | 1.38s | FAIL |
| p99 응답시간 (서버 측) | < 1.5s | 1.68s | FAIL |
| 핫스팟 동시 좋아요 정합성 | 손실 0% | 손실 87% | **FAIL** |

HTTP 레벨/평균 응답시간은 목표를 충족했지만, **꼬리 지연(p95/p99)과 데이터 정합성은 실패** —
이게 이번 회차의 핵심 발견이자 다음 회차(Redisson 분산락)의 개선 목표.

### DB 정합성 대조 (핫스팟 동시 좋아요 시나리오)

HTTP 응답만으로는 전부 정상(200 OK, 에러 0%)이었지만, DB를 직접 대조하니 **Lost Update**가 실측으로 재현됨.

| 항목 | 값 |
|---|---|
| 동시에 좋아요 누른 유저 수 | 100명 (서로 다른 유저) |
| 실제 `location_likes` row 개수 | 100개 (정확함, UNIQUE 제약은 정상 작동) |
| `location.like_count` 표시값 | 13 |
| 손실률 | 87% |

원인: `like_count` 갱신이 락 없는 read-modify-write(`count+1`) 방식이라 동시 요청끼리 서로 덮어씀.
UNIQUE 제약 덕분에 중복 좋아요 자체는 막혔지만, 카운터 컬럼만 조용히 틀어짐 — HTTP/에러 로그로는
드러나지 않고 DB 대조로만 발견 가능한 케이스.

### 서버 측 latency 지표 (Grafana/Prometheus, Micrometer 기반)

핫스팟 동시 좋아요 구간(13:23:25~13:23:30)에 맞춰 `traceK` 앱 대시보드에서 확인한 응답 지연 분포.

| 지표 | 값 |
|---|---|
| p50 (중앙값) | 177ms |
| 전체 평균 | 416ms |
| p95 | 1.38s |
| p99 | 1.68s |

JMeter 클라이언트 측 최대 응답시간(2361ms)과 서버 측 p99(1.68s)가 같은 자릿수로 일치 — 클라이언트에서
관측된 지연 스파이크가 서버 쪽에서도 동일하게 확인됨. p50은 낮게 유지되는 반면 p95/p99만 확 튀는 걸
보면, 동시 쓰기 경합이 전체 요청을 느리게 만든 게 아니라 **일부 요청에만 꼬리 지연(tail latency)**으로
나타남 — DB 정합성(Lost Update)뿐 아니라 지연시간 관점에서도 동시성 문제가 실측으로 뒷받침됨.

(참고: 이 서버는 대시보드 export 당시 루트 볼륨이 6.7GB로 거의 꽉 차서 Grafana 로그인 자체가
불안정했음 — 20GB로 확장 후 정상화. 1차 테스트 시점엔 이 이슈가 없었어서 수치 자체는 유효함.)

### 참고: 별도 발견된 한계 (이번 회차 범위 밖)

지인이 k6로 훨씬 큰 규모(수천~만 건 단위)를 같은 EC2 퍼블릭 IP로 시도했을 때 요청이 아예 도달하지
않는 현상 발생. 보안그룹은 8080 전체 오픈 상태였고 소규모 요청(curl 단발)은 정상 응답했던 것으로
보아, 네트워크/방화벽 문제가 아니라 **인스턴스 스펙(t2/t3.micro급 CPU 크레딧) 또는 Docker
port-proxy 병목**으로 추정됨. 실행 당시 서버 리소스 지표(Prometheus/Grafana)가 수집되고 있지
않아서 사후 확인 불가 — 확정 원인 아님, 향후 필요 시 재현 테스트 필요.

### 시나리오 4: 확인하려던 것

`LocationLikeCommandService.like()`는 설계상 "이미 좋아요 상태면 아무 동작 없이 성공 응답만
반환"하는 멱등 API. 코드 주석에 이미 알려진 한계가 명시돼 있었음: 동시 요청이 몰리면
`existsByUserIdAndLocationId` 체크를 여러 스레드가 동시에 통과한 뒤 UNIQUE 제약 위반이
**트랜잭션 커밋 시점에** 재발생할 수 있어, catch 블록이 못 잡고 500으로 새어나갈 가능성이 있음.

### 목표 SLA vs 실측

| 항목 | 목표 | 실측 | 판정 |
|---|---|---|---|
| HTTP 응답 | 30건 전부 200 OK | 27건 200 / **3건 500** | **FAIL** |
| DB `location_likes` row 수 (user 999, location 42) | 정확히 1개 | **정확히 1개** | PASS |
| `like_count` 증가량 (location 42) | 정확히 +1 | **정확히 1** | PASS |

**핵심 발견: 데이터는 100% 안전한데, 사용자 10명 중 1명꼴로 500 에러 화면을 본다.** 코드 주석에
예견돼있던 "커밋 시점 예외 재발생"이 실측으로 재현됨 — DB 정합성(멱등성)과 API 안정성(에러율)은
별개 문제라는 걸 보여주는 사례. Prometheus로 교차 검증(`status="500"` 카운터)해도 정확히
3건, `uri=/api/locations/{locationId}/likes, method=PUT, outcome=SERVER_ERROR`로 동일하게 잡힘 —
클라이언트(JMeter)·서버(Micrometer) 양쪽에서 일치.

### 시나리오 3: 핫스팟 동시 좋아요취소 (100명)

| 항목 | 값 |
|---|---|
| HTTP 응답 | 100건 전부 200 OK, 에러 0건 |
| DB `location_likes` 잔여 row (location 41) | **0개** — 정상 (전부 취소됨) |

DELETE는 UNIQUE 제약 위반 예외 경로가 없어서(존재 확인 후 삭제만 하면 됨) 시나리오 4와 달리
클라이언트 레벨 에러가 전혀 없었음. `like_count`는 이미 1차에서 손실 상태(13)였던 값이 이번
취소로 0까지 내려감 — `decreaseLikeCount()`에 0 미만 방지 가드(`current > 0 ? current-1 : 0`)가
있어서 음수는 안 나옴.

### 서버 측 latency/자원 지표 (Grafana/Prometheus)

| 지표 | 1차 (핫스팟 좋아요만) | 이번 (좋아요취소100 + 중복좋아요30) |
|---|---|---|
| p50 | 177ms | **555ms** |
| p95 | 1.38s | 1.02s |
| p99 | 1.68s | 1.34s |
| 전체 평균 | 416ms | 556ms |

1차는 p50이 낮게 유지되고 p95/p99만 튀는 "꼬리 지연" 패턴이었는데, 이번엔 **p50 자체가 크게
올라감** — DELETE 100명이 동시에 같은 카운터를 두고 경합하면서 부하가 더 넓게 퍼진 것으로 보임.

CPU 사용률은 낮았음(System/Process CPU 평균 15% 내외)에 반해 **Load Average(1m) 2.62**
(CPU 코어 2개 기준 과부하 신호) — CPU가 아니라 락/I/O 대기로 스레드가 쌓였다는 정황 증거.
"서버 자원 부족이 아니라 DB 경합이 원인"이라는 가설을 뒷받침.

(참고: "부하가 많이 걸리는 엔드포인트" 패널에서 `/api/test/auth/token/{userId}`가 가장 높게
찍히는데, 이건 dev 전용 테스트 토큰 발급 엔드포인트라 실제 서비스 API가 아님 — 130개 스레드가
각자 한 번씩 호출하는 테스트 하네스 오버헤드로 해석하면 됨.)
