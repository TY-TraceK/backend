# TraceK 부하테스트 기록

`tracek-load-test.jmx` 실행 결과를 회차별로 기록. 원본 리포트/raw 로그는
`scripts/jmeter/results/<회차>/`에 로컬 보관 (용량 문제로 git 추적 제외, `.gitignore` 참고).

## 1차 (Baseline) — 2026-08-14

- **실행 위치:** 로컬 PC → EC2 퍼블릭 IP(13.210.218.196:8080)
- **구성:** 1_전체_API_흐름(50 threads, 5 loop) + 2_핫스팟_동시_좋아요(같은 location_id에 서로 다른 유저 100명 동시 PUT)
- **원본:** `scripts/jmeter/results/baseline/result_baseline.jtl`, `report_baseline/index.html`

|---|---|---|---|

### DB 정합성 대조 (핫스팟 동시 좋아요 시나리오)

HTTP 응답만으로는 전부 정상(200 OK, 에러 0%)이었지만, DB를 직접 대조하니 **Lost Update**가 실측으로 재현됨.

| 항목 | 값 |
|---|---|
| 동시에 좋아요 누른 유저 수 | 100명 (서로 다른 유저) |
| 실제 `location_likes` row 개수 | 100개 (정확함, UNIQUE 제약은 정상 작동) |
| `location.like_count` 표시값 | 13 |
| 손실률 | 87% |

원인: `like_count` 갱신이 락 없는 read-modify-write(`count+1`) 방식이라 동시 요청끼리 서로 덮어씀.
UNIQUE 제약 덕분에 중복 좋아요 자체는 막혔지만, 카운터 컬럼만 조용히 틀어짐 — HTTP/에러 로그로는
드러나지 않고 DB 대조로만 발견 가능한 케이스.

### 서버 측 latency 지표 (Grafana/Prometheus, Micrometer 기반)

핫스팟 동시 좋아요 구간(13:23:25~13:23:30)에 맞춰 `traceK` 앱 대시보드에서 확인한 응답 지연 분포.

| 지표 | 값 |
|---|---|
| p50 (중앙값) | 177ms |
| 전체 평균 | 416ms |
| p95 | 1.38s |
| p99 | 1.68s |

JMeter 클라이언트 측 최대 응답시간(2361ms)과 서버 측 p99(1.68s)가 같은 자릿수로 일치 — 클라이언트에서
관측된 지연 스파이크가 서버 쪽에서도 동일하게 확인됨. p50은 낮게 유지되는 반면 p95/p99만 확 튀는 걸
보면, 동시 쓰기 경합이 전체 요청을 느리게 만든 게 아니라 **일부 요청에만 꼬리 지연(tail latency)**으로
나타남 — DB 정합성(Lost Update)뿐 아니라 지연시간 관점에서도 동시성 문제가 실측으로 뒷받침됨.

(참고: 이 서버는 대시보드 export 당시 루트 볼륨이 6.7GB로 거의 꽉 차서 Grafana 로그인 자체가
불안정했음 — 20GB로 확장 후 정상화. 1차 테스트 시점엔 이 이슈가 없었어서 수치 자체는 유효함.)

### 참고: 별도 발견된 한계 (이번 회차 범위 밖)

지인이 k6로 훨씬 큰 규모(수천~만 건 단위)를 같은 EC2 퍼블릭 IP로 시도했을 때 요청이 아예 도달하지
않는 현상 발생. 보안그룹은 8080 전체 오픈 상태였고 소규모 요청(curl 단발)은 정상 응답했던 것으로
보아, 네트워크/방화벽 문제가 아니라 **인스턴스 스펙(t2/t3.micro급 CPU 크레딧) 또는 Docker
port-proxy 병목**으로 추정됨. 실행 당시 서버 리소스 지표(Prometheus/Grafana)가 수집되고 있지
않아서 사후 확인 불가 — 확정 원인 아님, 향후 필요 시 재현 테스트 필요.

### 시나리오 4: 확인하려던 것

`LocationLikeCommandService.like()`는 설계상 "이미 좋아요 상태면 아무 동작 없이 성공 응답만
반환"하는 멱등 API. 코드 주석에 이미 알려진 한계가 명시돼 있었음: 동시 요청이 몰리면
`existsByUserIdAndLocationId` 체크를 여러 스레드가 동시에 통과한 뒤 UNIQUE 제약 위반이
**트랜잭션 커밋 시점에** 재발생할 수 있어, catch 블록이 못 잡고 500으로 새어나갈 가능성이 있음.

### 목표 SLA vs 실측

| 항목 | 목표 | 실측 | 판정 |
|---|---|---|---|
| HTTP 응답 | 30건 전부 200 OK | 27건 200 / **3건 500** | **FAIL** |
| DB `location_likes` row 수 (user 999, location 42) | 정확히 1개 | **정확히 1개** | PASS |
| `like_count` 증가량 (location 42) | 정확히 +1 | **정확히 1** | PASS |

**핵심 발견: 데이터는 100% 안전한데, 사용자 10명 중 1명꼴로 500 에러 화면을 본다.** 코드 주석에
예견돼있던 "커밋 시점 예외 재발생"이 실측으로 재현됨 — DB 정합성(멱등성)과 API 안정성(에러율)은
별개 문제라는 걸 보여주는 사례. Prometheus로 교차 검증(`status="500"` 카운터)해도 정확히
3건, `uri=/api/locations/{locationId}/likes, method=PUT, outcome=SERVER_ERROR`로 동일하게 잡힘 —
클라이언트(JMeter)·서버(Micrometer) 양쪽에서 일치.

### 시나리오 3: 핫스팟 동시 좋아요취소 (100명)

| 항목 | 값 |
|---|---|
| HTTP 응답 | 100건 전부 200 OK, 에러 0건 |
| DB `location_likes` 잔여 row (location 41) | **0개** — 정상 (전부 취소됨) |

`LocationLikeCommandService.like()`/`unlike()`에서 락 획득을 가장 먼저 수행하도록 구현

### 배포 사고: 옛날 이미지로 테스트했던 첫 시도

락 코드를 커밋한 직후 재측정했을 때 손실률이 87% → 19%로 개선된 것처럼 보였지만(`round-a`),

고치고 실제 배포(재빌드+재기동)를 안 한 상태로 테스트한 것. develop에 PR을 머지해 CI/CD로
정식 배포한 뒤부터 정확한 측정이 시작됨. **교훈: 부하테스트 전에 반드시 배포 이미지 빌드 시각을

### round-b: 비관적 락 배포 후 1차 재측정 — 부분 성공

| 항목 | 1차 baseline | round-b (비관적 락) | 판정 |
|---|---|---|---|
| 시나리오2 손실률 (100명 동시 좋아요) | 87% | **0%** (row=100, count=100) | PASS |
| 시나리오4 500 에러 (동일유저 중복좋아요 30명) | - | **4/30건 (13.3%)** | FAIL |

시나리오2(서로 다른 유저)는 완벽하게 고쳐졌지만, 시나리오4(같은 유저 반복 요청)에서
여전히 `Duplicate entry '999-42'` UNIQUE 위반이 서버 로그에서 4건 확인됨 — 클라이언트 측
500 4건과 정확히 일치.

**원인 분석 (MySQL REPEATABLE READ 스냅샷 문제):** `like()`의 실행 순서가
`validateActiveUser`(일반 SELECT) → `findByIdForUpdate`(락 읽기) → `existsBy...`(일반 SELECT)
였음. MySQL REPEATABLE READ에서는 트랜잭션의 **첫 번째 일반(락 없는) SELECT 시점에 컨시스턴트
읽기 스냅샷이 고정**되고, 이후 같은 트랜잭션의 다른 일반 SELECT도 전부 그 스냅샷을 그대로 씀.
락을 건 읽기(`FOR UPDATE`)는 스냅샷을 무시하고 항상 최신 커밋을 읽지만, 그게 트랜잭션의
"첫 읽기"가 아니라 **두 번째** 읽기였기 때문에 아무 효과가 없었음 — `validateActiveUser`가
이미 락 대기 *이전 시점*에 스냅샷을 고정시켜버려서, 락을 획득한 뒤에 실행되는 `existsBy`도
여전히 그 낡은 스냅샷을 보고 "아직 안 눌렀네" 하고 중복 INSERT를 시도한 것.

### 수정: 락 읽기를 트랜잭션의 첫 DB 작업으로 이동 (PR #106)

`findByIdForUpdate`를 `validateActiveUser`보다 먼저 호출하도록 순서만 변경. 회귀 방지를 위해
테스트에도 `Mockito InOrder`로 이 순서를 명시적으로 고정함(CodeRabbit 리뷰로 발견 — 기존
테스트는 순서가 깨져도 통과할 수 있었음).

### round-c: 최종 검증 — 완전 해결

| 항목 | 1차 baseline | round-b | round-c (최종) |
|---|---|---|---|
| 시나리오2 손실률 | 87% | 0% | **0%** (row=100, count=100) |
| 시나리오4 500 에러 | - | 4/30건 | **0/30건** |
| 전체 에러율 (2263건) | - | - | **0.00%** |

시나리오4 DB 대조: `location_likes` row=1, `like_count`=1 — 정확히 일치. 사후검증
(tearDown Thread Group의 `likeCount==1` 자동 assertion)도 통과.

**Before → After 요약:**
1. 1차 baseline: 손실률 87%, 락 없음
2. 비관적 락 적용(1차): 손실률 0%로 개선됐지만, 스냅샷 타이밍 문제로 일부 요청(13.3%)이 여전히 500
3. 락 읽기 순서 수정: 손실률 0%, 에러율 0% — 완전 해결

**교훈:** 락을 거는 것만으로는 부족하고, 그 락이 트랜잭션의 *첫* DB 작업이어야 DB 격리수준(여기선
MySQL REPEATABLE READ)의 스냅샷 타이밍과 충돌하지 않는다는 걸 실측으로 확인함. 원인은
SQL 벤더나 프레임워크가 알려주지 않고, 락 도입 후에도 남아있는 잔여 에러율을 실제로 재측정해서
DB 로그(`Duplicate entry`)까지 파고들어야 발견 가능했음.

### round-c 서버 측 latency/자원 지표 (Grafana) — 1차(락 적용 전)와 비교

1차 부하테스트는 baseline(시나리오 1+2, 8/14)과 1-보강(시나리오 3+4, 8/18) 두 번에 걸쳐
돌았음 — 둘 다 락 적용 *전* 상태라 "1차" 범주로 같이 봐야 함. round-c(1+2+4 통합)와 정확히
겹치는 구성은 없지만, 1-보강 쪽에 시나리오4(동일유저 중복좋아요) latency가 이미 있어서
round-c와 더 관련 있는 참고점임.

| 지표 | 1차 baseline (1+2) | 1차 1-보강 (3+4, 시나리오4 포함) | round-c (락 적용 후, 1+2+4) |
|---|---|---|---|
| p50 | 177ms | 555ms | 120ms |
| 전체 평균 | 416ms | 556ms | 230ms |
| p95 | 1.38s | 1.02s | 523ms |
| p99 | 1.68s | 1.34s | 3.90s |
| Load Average(1m) 최대 | - | - | 2.84 (코어 2개) |
| Process CPU 최대 | - | - | 92.2% |

**⚠️ 비교 한계:** 세 라운드 모두 시나리오 구성이 서로 다름(1+2 / 3+4 / 1+2+4) — 동일 구성으로
맞춘 게 하나도 없어서, 위 표 하나만으로 p50/p95/p99 변화를 비관적 락 하나만의 효과로 단정할
수 없음. 대신 JMeter raw 결과(`result.jtl`)를 라벨별로 뜯어서 아래처럼 직접 검증함.

### round-c/round-d 교차 분석 — p99 폭증의 진짜 원인 (raw jtl 데이터 기반)

**1. 순수 비관적 락 오버헤드 (round-d, 시나리오3 단독):**

| 지표 | baseline 무락 핫스팟 (`01_동시_좋아요`) | round-d 락 적용 (`01_동시_좋아요취소`) |
|---|---|---|
| p50 | 1250ms | 1173ms |
| p95 | 1747ms | 1963ms |
| p99 | 1943ms | 2001ms |
| max | 1943ms | 2001ms |

무락 baseline(p99 1943ms) 대비 비관적 락 단독 실행(p99 2001ms)의 지연 증가는 미미함 — 동시
100건 경합 시에도 비관적 락의 순수 직렬화 비용 자체는 약 2초 수준으로 안정적으로 제어됨.
round-d는 CPU 12.4%/Load 0.30으로 여유로운 조건이라 락의 "순수 비용"이 가장 깨끗하게 드러남.

**2. 복합 부하 시 p99 폭증 원인 규명 (round-c, 시나리오 1+2+4 동시 실행):**

round-c에서 `01_동시_좋아요` 라벨만 따로 보면 p50=3879ms, p95=5787ms, p99=6020ms —
round-d(단독 락)보다 3배 가까이 나쁨. 그런데 락과 전혀 무관한 엔드포인트도 같이 튐:

| 라벨 | baseline max | round-c max |
|---|---|---|
| `00_토큰_발급` | 2361ms | 4774ms |
| `01_관광지_목록` | 1856ms | 4105ms |
| `02_관광지_상세` | 728ms | 4882ms |

`FOR UPDATE`는 같은 row를 잡으려는 트랜잭션끼리만 직렬화하므로, 토큰 발급·목록 조회처럼 그
row와 무관한 요청이 2~6배 느려질 이유가 없음. round-c는 시나리오 1+2+4(총 380여 건)를
한꺼번에 돌리면서 2코어 서버가 CPU 92.2%/Load 2.84까지 포화됐고(round-d는 CPU 12.4%/Load
0.30), 이 **"여러 시나리오 동시 실행에 따른 CPU 포화"**가 p99 6초 폭증의 주원인으로 훨씬
설득력 있음. 락과 무관한 Read/Auth 엔드포인트까지 동반 지연된 점이 이를 뒷받침함.

**3. 종합 판단:** 비관적 락은 CPU 자원이 충분하다면 핫스팟 경합 상황에서도 100% 정합성을
유지하며 안정적인 지연 시간(p99 ~2s)을 제공함. 다만 CPU 포화 상태에서는 DB Connection
점유 시간 지연과 복합 작용해 시스템 전체의 Tail Latency를 가중시킬 수 있음 — 동일 구성
재측정(예: 1+2+4 모두 동시 vs 시나리오2만 단독)으로 CPU 포화와 락 큐잉의 기여도를 더
정밀하게 분리하는 게 다음 확인 대상.

### round-d: 좋아요취소(unlike) 방향 검증 — 완전 해결

round-c에서 시나리오2로 쌓아둔 좋아요 100개(location 41, row=100/count=100) 상태를 그대로 두고,
시나리오3(핫스팟 동시 좋아요취소, 100명)만 이어서 실행 — jmx 설계상 원래 "2번 실행 후 결과
확인하고 켜서 재실행"하도록 되어있던 시나리오라, round-c 직후가 정확한 실행 시점이었음.

| 항목 | 값 |
|---|---|
| HTTP 응답 | 100건 전부 200 OK, 에러 0건 |
| DB `location_likes` 잔여 row | **0개** |
| `location.like_count` | **0** |

증가(시나리오2) 방향뿐 아니라 **감소(시나리오3) 방향도 정합성 100% 확인**. 100개 좋아요가
100명 동시 취소로 정확히 0까지 내려감 — Lost Update 없음.

### round-d 서버 측 latency/자원 지표 (Grafana)

| 지표 | 값 |
|---|---|
| p50 | 133ms |
| 전체 평균 | 500ms |
| p95 | 1.62s |
| p99 | 1.76s |
| Load Average(1m) 최대 | 0.30 (낮음) |
| Process CPU 최대 | 12.4% (낮음) |

CPU/Load가 눈에 띄게 낮은데도(단독 시나리오라 부하 자체가 작음) p95(1.62s)·p99(1.76s)가
p50(133ms) 대비 튀지만, 위 "round-c/round-d 교차 분석"에서 확인했듯 이건 round-c의
CPU 포화형 폭증(p99 6.02s)과는 다른 현상 — round-d는 락의 순수 직렬화 비용(~2s)에 가까움.
round-d는 시나리오3 하나만 돈 결과라 round-c보다 훨씬 깨끗한 비교 조건임.

**CodeRabbit 리뷰 반영 — 측정 범위를 CPU/Load 밖으로 넓혀서 확인:**

| 자원 | 측정값 | 판정 |
|---|---|---|
| JVM Heap (Old Gen) | 66.6MB / 501MB | 여유 충분 |
| GC pause 최대 | 27ms | 무시 가능 |
| GC 발생 횟수 (윈도우 내) | ~1회 | 무시 가능 |
| HikariCP 풀 크기 | 10 | - |
| **HikariCP 커넥션 획득 대기(`acquire_seconds_max`)** | **관측 시간창 내 최대 1.6초** | 커넥션 획득 대기와 일치하는 관측 |
| 디스크 I/O / 네트워크 | 측정 불가 (node-exporter 미연결) | 미확인 |

메모리/GC는 확정적으로 배제됨(수치가 충분히 낮음). HikariCP 쪽은 **최대 1.6초의 커넥션 획득
지연이 관측**됐음 — 다만 `_seconds_max`는 앱 시작 이후 누적 최대값이 아니라 Micrometer
`TimeWindowMax`(기본 step 1분 × bufferLength 3 = 약 3분 슬라이딩 창, 새 값이 없으면 0으로
리셋)라, 정확히 round-d 테스트 순간의 값이라고 단정할 순 없고 "그 시간창 안에서 관측된 최댓값"
정도로 봐야 함. `active`/`idle`/`pending` 게이지가 스크랩 시점에 0/10/0으로만 보인 것도(테스트가
6초짜리라 스크랩 주기 사이 피크를 놓쳤을 가능성) 같은 맥락. 이 값 하나로 "100개 요청이 10개
풀을 두고 경합했다"를 **직접 증명하는 건 아니고**, 커넥션 획득 대기가 있었다는 것과 일치하는
관측 정도로 해석하는 게 정확함 — row 락 대기와 HikariCP 대기, 둘 중 무엇이 더 크게 기여했는지는
이 지표만으로 분리 불가.

**결론 (범위를 좁혀서):** CPU/메모리/GC 병목은 아님이 확인됨. p95/p99 지연은 "같은 row 락
대기"와 "HikariCP 풀 자체의 커넥션 획득 대기"가 함께 작용했을 가능성이 높음 — 다만 정확히
어느 쪽이 더 크게 기여했는지는 DB 레벨 락 대기 시간(`SHOW ENGINE INNODB STATUS`,
`performance_schema`)을 직접 재지 않는 한 분리할 수 없음. 디스크 I/O·네트워크는 이번
모니터링 구성으로는 측정 불가라 별도 확인 대상으로 남겨둠.

## 3차: 낙관적 락(Optimistic Lock) 적용 — 2026-08-19~20

`feat/SCRUM-61-optimistic-lock` 별도 브랜치에서 진행(#109) — develop 미반영, EC2에 수동
배포(`git checkout` + 재빌드)로만 테스트. `Location`에 `@Version` 추가,
`findByIdWithOptimisticLock`(`LockModeType.OPTIMISTIC`), 재시도 래퍼
(`LocationLikeCommandService`)와 실제 `@Transactional` 로직(`LocationLikeTransactionalWriter`)을
별도 빈으로 분리해 구현.

### 구현 중 발견된 버그 3개

1. **self-invocation으로 `@Transactional` 무시됨** — 재시도 루프와 트랜잭션 로직이 같은
   빈 안에 있어서 `this.메서드()` 호출이 프록시를 안 거침. 배포 전 코드리뷰로 발견, 빈 분리로 해결.
2. **기존 row `version` NULL로 인한 100% 실패** (무효 라운드, 파일 삭제함) —
   `Cannot invoke "Object.equals(Object)" because ... "EntityEntry.getVersion()" is null`.
   `@Version` 컬럼을 Hibernate `ddl-auto=update`로 추가하면 기존 row는 NULL로 남는데,
   이 상태로 커밋하면 100% 실패함. `UPDATE location SET version=0 WHERE version IS NULL;`
   백필로 해결 — 실서비스라면 스키마 마이그레이션 스크립트에 포함해야 할 부분.
3. **`UnexpectedRollbackException`** (round-f, 시나리오4 6/30건 500) — `saveLike()`의
   `DataIntegrityViolationException`을 `@Transactional` 메서드 안에서 잡아 삼켰지만,
   Spring이 이미 트랜잭션을 rollback-only로 표시한 뒤라 커밋 시점에 다른 예외가 대신 발생함
   (비관적 락 땐 완전 직렬화라 이 경로 자체가 실행된 적이 없어서 안 드러났던 버그). 트랜잭션
   밖(재시도 래퍼)에서 "이미 저장됨 = 성공"으로 처리하도록 수정.

### round-h: 재시도 10회 + 지수 백오프(Full Jitter)로 튜닝 후

고정 지터 대신 지수 백오프+Full Jitter(AWS 아키텍처 블로그 표준 패턴) 적용:
`sleep = random(0, min(500ms, 20ms * 2^retryCount))`.

| 항목 | round-g (5회, 고정지터) | round-h (10회, 지수백오프) |
|---|---|---|
| 시나리오2 성공률 (클라이언트 기준) | 51% | 81% |
| 시나리오2 DB 실제 반영 개수 | 51 | **83** |
| 전체 에러율 | 2.17% | 0.84% |

**새로 발견된 트레이드오프:** DB엔 83개가 반영됐는데 클라이언트는 81건만 성공으로 관측함 —
재시도 대기가 길어지면서 서버는 결국 성공했는데 클라이언트(JMeter 10초 타임아웃)가 먼저
포기해버린 것으로 보임(`SocketTimeoutException` 3건 관측). 재시도를 늘릴수록 성공률은
오르지만, 그만큼 길어진 대기시간이 클라이언트 타임아웃과 충돌할 위험이 커짐.

### round-i-unlike: 좋아요취소(감소) 방향 검증

round-h가 남긴 좋아요 83개 위에서 시나리오3(핫스팟 동시 좋아요취소, 100명)만 이어서 실행
(비관적 락 round-d와 동일한 방식 — round-h 직후가 정확한 실행 시점).

| 항목 | 값 |
|---|---|
| HTTP 응답 | 93/100 성공(200), 7건 CONCURRENCY_ERROR(409) |
| DB `location_likes` 잔여 row | 7개 |
| `location.like_count` | 7 |

93건의 200 중 실제로는 76건이 진짜 삭제(83개 있던 것 중), 17건은 애초에 좋아요가 없던
유저라 no-op으로 성공 처리됨(76+17=93 일치). 재시도를 다 소진한 7명의 좋아요는 그대로
남아 `count`=`row`=7로 정확히 일치 — **증가/감소 양방향 모두 Lost Update 없이 정합성
유지됨**을 확인.

### round-h/round-i-unlike 서버 측 latency/자원 지표 (Grafana) — 비관적 락과 비교

round-g/h/i-unlike는 실행 당시 Grafana CPU/Load를 따로 기록해두지 않았는데, 이후 확보한
스크린샷(round-h: 02:36:00 구간, round-i-unlike: 02:43:59~02:44:28 구간 — 각각의 jtl
실행 시각과 대조해 확인함)으로 보강함.

| 지표 | round-h (낙관적 락, 1+2+4 동시) | round-c (비관적 락, 1+2+4 동시) | round-i-unlike (낙관적 락, 시나리오3 단독) | round-d (비관적 락, 시나리오3 단독) |
|---|---|---|---|---|
| Process CPU 최대 | 81.5% | 92.2% | 25.8% | 12.4% |
| System CPU 최대 | 95.7% | - | 31.8% | - |
| Load Average(1m) 최대 | 3.59 | 2.84 | 0.29 | 0.30 |
| Grafana p99 (집계) | 1.88s | 3.90s | 3.94s | 1.76s |
| jtl 핫스팟 라벨 p99 | 10.00s(JMeter 타임아웃) | 6.02s | 4.29s | 2.00s |

**1. 단독 조건(round-i-unlike vs round-d) — CPU/Load 둘 다 낮음.** 낙관적 락 단독 실행도
CPU 25.8%/Load 0.29로 여유로운데, 그런데도 핫스팟 라벨 p99(4.29s)는 비관적 락 단독(2.00s)
보다 2배 이상 높음 — **CPU/시스템 자원 문제가 아니라 재시도+백오프 구조 자체의 비용**이라는
게 실측으로 확정됨(이전 절의 "종합 판단 2"와 일치).

**2. 복합 조건(round-h vs round-c) — 낙관적 락도 CPU/Load가 비관적 락 못지않게 포화됨.**
round-h의 Load Average 최대(3.59)는 round-c(2.84)보다 오히려 높고, Process CPU(81.5%)도
근접한 수준. 앞서(round-i-unlike 스크린샷 확보 전) "무관 엔드포인트 collateral 지연이
round-c보다 작으니 CPU 포화도 약했을 것"이라고 추정했던 부분은 **실측 결과 틀렸음** — 낙관적
락도 고경합 복합 부하에서 시스템 자원을 비관적 락만큼, 혹은 그 이상 소모함. 재시도마다
트랜잭션을 처음부터 다시 실행하기 때문에 실패한 시도까지 포함한 총 작업량이 더 많아지는 게
원인으로 보임(확정은 아니고 정황상 추정).

**3. 주의 — Grafana 집계 p99는 핫스팟을 가림.** round-h의 Grafana 집계 p99(1.88s)만 보면
round-c(3.90s)보다 나아 보이지만, 실제 핫스팟 라벨(jtl)의 p99는 round-h가 10초 타임아웃까지
갔고 round-c는 6.02초로 오히려 round-h보다 나음. 집계 p99는 2000여 건의 무관한 빠른 요청에
섞여 핫스팟 성능을 가리므로, 락 전략 비교는 집계 수치가 아니라 반드시 라벨(엔드포인트)별로
봐야 함.

### 비관적 락 vs 낙관적 락 (고경합 시나리오 기준) 종합

| 항목 | 비관적 락 (round-c/d) | 낙관적 락 (round-h/round-i, 튜닝 후) |
|---|---|---|
| 시나리오2 성공률 | 100% | 81% (DB 기준 83%) |
| 시나리오3 성공률 | 100% | 93% |
| 정합성(성공분) | 완벽 | 완벽 |
| 전체 에러율 | 0.00% | 0.84%~3.5% |
| 실패 시 동작 | 없음 (대기 후 결국 성공) | 명시적 에러 (사용자에게 재시도 요구) |
| 단독 조건 CPU/Load | 12.4% / 0.30 | 25.8% / 0.29 |
| 복합 조건 CPU/Load | 92.2% / 2.84 | 81.5% / **3.59** |

**중간 판단:** "좋아요"는 인기 컨텐츠에 핫스팟이 몰리기 쉬운 기능이라, 비관적 락처럼 "느릴 순
있어도 항상 성공"하는 쪽이 UX상 더 안전해 보임. 게다가 낙관적 락은 단독 조건에서도 재시도
구조 자체의 비용으로 비관적 락보다 느리고, 복합 조건에서는 시스템 자원도 비관적 락 못지않게
쓰면서 실패율(409)까지 발생시켜 — 자원 사용량 측면에서 뚜렷한 이점이 없음. 다만 이번
라운드는 일부러 100명 동시 핫스팟만 재본 것이라, **저경합(일반적인 트래픽) 상황에서 낙관적
락의 오버헤드 이점**까지 확인해야 최종 판단이 완결됨 — 다음 라운드에서 진행 예정.
